1. SYSTEM OVERVIEW & CORE STACK
====================================================================================================
HabeshaFreight is a digital freight marketplace backend engineered specifically for the regional 
and long-haul road transportation ecosystem in Ethiopia. The platform directly connects verified 
Shippers (cargo owners) with verified Drivers and Fleet Owners (carriers), replacing legacy 
phone-broker chains with an automated, transparent, secure, and audited digital workflow.

Core Technical Stack:
- Runtime Environment: Node.js (v20+ LTS)
- Programming Language: TypeScript 5.4 (Strict Type Checking Enabled)
- Web Framework: Express.js 4.19
- Database Engine: PostgreSQL 14+ with PostGIS Spatial Extension
- Database ORM / Query Builder: Knex.js 3.1.0 with TypeScript Migration/Seeder Tooling
- Authentication & Cryptography: JSON Web Tokens (jsonwebtoken 9.0), bcryptjs (2.4.3), SHA-256 OTP Hashes
- Security Middleware: Helmet 7.1.0, CORS 2.8.5, Express Rate Limit 8.6.2
- File Upload Management: Multer 2.2.0 (Stored in local storage / uploads)
- Testing Framework: Native Node.js Test Runner with tsx & Supertest (32/32 Endpoints Verified)

3. DATA LAYER & DATABASE SCHEMA DESIGN
====================================================================================================
The database schema consists of 14 core relational tables managed via Knex migrations:

1. `users`
   - Primary Key: id (UUID v4)
   - Core Fields: full_name, email (unique), phone_number (unique), password_hash, role
     ('SHIPPER', 'DRIVER', 'FLEET_OWNER', 'ADMIN')
   - Identity & Security: is_verified (boolean), kyc_status ('PENDING', 'APPROVED', 'REJECTED'),
     status ('ACTIVE', 'SUSPENDED', 'DEACTIVATED'), otp_code, otp_expires_at
   - National Identification: fayda_number, fayda_verified (boolean)
   - Driver/Company Metadata: license_number, license_photo_url, company_registration_number,
     last_lat, last_lng, last_location_updated_at

2. `vehicles`
   - Primary Key: id (UUID v4)
   - Foreign Key: driver_id -> users(id)
   - Vehicle Metadata: plate_number, vehicle_type ('ISUZU', 'SINO_TRUCK', 'TRAILER', 'PICKUP'),
     capacity_tons, is_active, verification_status ('PENDING', 'VERIFIED', 'REJECTED')
   - Geospatial Origin: origin_lat, origin_lng

3. `loads`
   - Primary Key: id (UUID v4)
   - Foreign Key: shipper_id -> users(id)
   - Cargo Specifications: cargo_description, weight_tons, origin_city, destination_city,
     origin_lat, origin_lng, destination_lat, destination_lng, offered_price_etb
   - Lifecycle Status: status ('POSTED', 'MATCHED', 'DISPATCHED', 'IN_TRANSIT', 'DELIVERED', 'CANCELLED')

4. `bids`
   - Primary Key: id (UUID v4)
   - Foreign Keys: load_id -> loads(id), driver_id -> users(id), vehicle_id -> vehicles(id)
   - Offer Details: bid_amount_etb, status ('PENDING', 'ACCEPTED', 'REJECTED')

5. `shipments`
   - Primary Key: id (UUID v4)
   - Foreign Keys: load_id -> loads(id), carrier_id -> users(id), vehicle_id -> vehicles(id)
   - Execution Status: status ('ASSIGNED', 'DISPATCHED', 'IN_TRANSIT', 'DELIVERED', 'CANCELLED', 'DISPUTED')
   - OTP Handover Hashes: pickup_otp_hash (SHA-256), delivery_otp_hash (SHA-256),
     pickup_verified_at, delivery_verified_at

6. `escrow_ledger`
   - Primary Key: id (UUID v4)
   - Foreign Keys: shipment_id -> shipments(id), payer_id -> users(id), beneficiary_id -> users(id)
   - Financial Calculations: gross_amount_etb, commission_amount_etb (5% platform fee),
     net_payout_amount_etb
   - Gateway Integrity: gateway_reference (Telebirr/Chapa reference), idempotency_key (Unique key)
   - Financial Status: status ('PENDING', 'LOCKED', 'RELEASED', 'REFUNDED', 'DISPUTED'), locked_at, released_at

7. `location_breadcrumbs`
   - Primary Key: id (UUID v4)
   - Foreign Keys: shipment_id -> shipments(id), driver_id -> users(id)
   - Telemetry Data: latitude, longitude, speed, recorded_at

8. `disputes`
   - Primary Key: id (UUID v4)
   - Foreign Keys: shipment_id -> shipments(id), raised_by_id -> users(id), resolved_by_id -> users(id)
   - Details: category ('DAMAGE', 'DELAY', 'PAYMENT', 'OTHER'), reason, status ('OPEN', 'UNDER_REVIEW', 'RESOLVED', 'REJECTED'), resolution_notes

9. `reviews` & `ratings`
   - Reviewer, reviewee, rating score (1 to 5 stars), commentary, shipment binding.

10. `messages`
    - In-app communications between shipper and carrier bound by shipment ID.

11. `company_drivers`
    - Fleet management mapping linking fleet owner users to attached driver users.

12. `audit_logs`
    - Administrative and security event audit trail storing user_id, action, target_type, target_id, details (JSON), and IP address.

4. SECURITY PROTOCOLS & AUTHENTICATION MECHANICS
====================================================================================================
The backend implements multi-layered defense mechanisms to safeguard identity, financial assets, 
and cargo operations:

1. Authentication Mechanics:
   - Multi-Factor Registration / Verification: Requires phone number and email address. 
     A 6-digit cryptographically random OTP is generated with a 15-minute validity window.
   - JWT Bearer Authentication: Authenticated users receive a signed JSON Web Token containing
     userId, role, email, and phone_number. Tokens expire in 24 hours (configurable).
   - Password Cryptography: All user passwords are salted and hashed using `bcryptjs` prior to storage.
   - National Identity (Fayda ID) Integration: System allows binding and verifying Ethiopian
     Fayda Digital National ID numbers to prevent duplicate accounts and fraud.

2. Cargo Handover Verification (Pickup & Delivery OTPs):
   - When a bid is accepted, the system generates two distinct random 6-digit OTPs (Pickup & Delivery).
   - Only the raw OTP hashes (SHA-256 algorithm via `crypto`) are stored in the `shipments` table.
   - Shipper provides the Pickup OTP to the driver at origin; Driver submits it via API.
   - Receiver provides Delivery OTP to driver at destination; Driver submits it via API.
   - The backend hashes the submitted input and checks for exact equality against stored SHA-256 hashes,
     preventing driver spoofing or false delivery claims.

3. Financial Ledger Protection & Idempotency:
   - Every escrow transaction requires a unique `idempotency_key` (format: IDEM-{shipment_id}-{timestamp}).
   - Webhook processing checks transaction state to prevent duplicate credit/payout allocations.
   - Automatic 5% platform commission calculation takes place at escrow creation time.

4. Network & Input Infrastructure Protection:
   - Helmet HTTP Security Headers: Disables x-powered-by header, enforces strict origin policies,
     and guards against XSS / clickjacking attacks.
   - Rate Limiting Guards:
     * Standard Rate Limiter: 100 requests per 15-minute window per IP.
     * Strict Rate Limiter: 20 requests per 5-minute window for sensitive endpoints (auth/payments).
   - CORS Policy: Configured to enforce trusted origin policies while allowing static uploaded doc access.

5. ROLE-BASED ACCESS CONTROL (RBAC) & AUTHORIZATION MODELS
====================================================================================================
Authorization is enforced at the router level using `authenticateToken` and `authorizeRoles` middlewares.

Supported User Roles:
1. `SHIPPER`
   - Can post cargo loads, view submitted bids, accept/reject bids on own loads.
   - Can deposit escrow funds via Telebirr/Chapa.
   - Can track live location of assigned drivers.
   - Can open disputes on assigned shipments.

2. `DRIVER`
   - Can search nearby loads using spatial radius matching.
   - Can submit bids on posted loads (validated against vehicle payload capacity).
   - Can update real-time GPS location coordinates.
   - Can input Pickup OTP to transition shipment to `IN_TRANSIT`.
   - Can input Delivery OTP to transition shipment to `DELIVERED` and trigger escrow release.

3. `FLEET_OWNER`
   - Manages company profile, vehicle fleet assets, and attached company drivers.
   - Receives aggregated revenue metrics and trip summaries.

4. `ADMIN`
   - Has full platform oversight: access to Admin Dashboard, Analytics, and System Health metrics.
   - Manages User Directory (Activate, Suspend, Soft-Delete, Role Changes).
   - Operates KYC Verification Queue & Vehicle Verification Queue.
   - Overrides shipment states and resolves open disputes (deciding between refunding shipper or releasing funds to carrier).
   - Views immutable system audit logs.

6. GEOSPATIAL & SPATIAL MATCHING INFRASTRUCTURE
====================================================================================================
The system utilizes PostgreSQL PostGIS spatial extension paired with a Haversine distance algorithm 
service (`SpatialService`):

Key Spatial Capabilities:
1. Load Spatial Discovery (`GET /api/loads/nearby`):
   - Accepts origin coordinates (lat, lng), search radius (radius_km, default 50km), and optional
     minimum vehicle capacity filter.
   - Computes exact distance from driver origin to load pickup location in kilometers.
   - Sorts results by distance ascending.

2. Vehicle Fleet Discovery (`GET /api/vehicles/nearby`):
   - Finds verified and active vehicles registered near a given coordinate.

3. Real-Time Location Breadcrumbs (`POST /api/tracking/location`):
   - Drivers emit periodic GPS updates.
   - Updates `last_lat` and `last_lng` on `users` table.
   - Inserts historical telemetry point into `location_breadcrumbs` table for full trip replay.

7. FINANCIAL LEDGER, ESCROW & PAYMENT WEBHOOKS
====================================================================================================
HabeshaFreight operates a multi-step escrow ledger (`escrow_ledger`):

1. Deposit Initiation (`POST /api/escrow/deposit`):
   - Shipper initiates payment for an assigned shipment.
   - Calculates Platform Commission (5%) and Net Driver Payout (95%).
   - Status set to `LOCKED` upon payment gateway approval (Telebirr, Chapa, CBE Birr).

2. Payment Webhook Listener (`POST /api/escrow/webhook`):
   - Listens for asynchronous transaction callbacks from payment gateways.
   - Verifies `idempotency_key`.
   - Updates status from `PENDING` to `LOCKED`.

3. Funds Release (`POST /api/shipments/:id/delivery-verify` or `POST /api/escrow/:id/release`):
   - Upon successful Delivery OTP verification, the escrow status automatically transitions to `RELEASED`.
   - Net payout amount becomes available for driver payout.

4. Refund Process (`POST /api/escrow/:id/refund`):
   - In case of cancelled shipments or admin dispute resolution in favor of the shipper, escrow status set to `REFUNDED`.

8. END-TO-END BUSINESS WORKFLOWS & DATA FLOWS
====================================================================================================

Flow 1: User Onboarding, OTP Verification & KYC Compliance
----------------------------------------------------------------------------------------------------
[User] --(Registers with Email/Phone/Role)--> [POST /api/auth/register]
                                                       |
                                            (Hashes Password with bcrypt)
                                            (Generates 6-Digit OTP)
                                            (Saves User Record)
                                                       |
                                        (Background Email/SMS Dispatch)
                                                       |
[User] --(Submits Received OTP)-------------> [POST /api/auth/verify-otp]
                                                       |
                                           (Validates OTP & Expiry)
                                           (Sets is_verified = true)
                                           (Issues JWT Bearer Token)
                                                       |
                  +------------------------------------+------------------------------------+
                  |                                                                         |
          [Role == SHIPPER]                                                  [Role == DRIVER / FLEET_OWNER]
                  |                                                                         |
         (kyc_status = APPROVED)                                                  (kyc_status = PENDING)
         (Full Access Granted)                                                    (Requires Admin KYC Approval)
                                                                                            |
                                                                              [Admin Approves Document Queue]
                                                                                            |
                                                                                  (kyc_status = APPROVED)


Flow 2: Cargo Listing, Spatial Search & Bidding
----------------------------------------------------------------------------------------------------
[Shipper] --(Posts Cargo Details & Price)--> [POST /api/loads] --> (Load Record Created, status = POSTED)
                                                                            |
[Driver]  --(Searches Nearby Cargo)--------> [GET /api/loads/nearby?lat=...&lng=...]
                                                                            |
                                                    (SpatialService computes Haversine distances)
                                                    (Returns array of loads sorted by proximity)
                                                                            |
[Driver]  --(Submits Price Offer)----------> [POST /api/bids]
                                                                            |
                                                    (Validates Vehicle Capacity >= Cargo Weight)
                                                    (Bid Created, status = PENDING)


Flow 3: Bid Acceptance, Escrow Deposit & Shipment Creation
----------------------------------------------------------------------------------------------------
[Shipper] --(Accepts Driver Bid)-----------> [PATCH /api/bids/:id/status]
                                                       |
                                           (Bid Status = ACCEPTED)
                                           (Other Load Bids = REJECTED)
                                           (Load Status = MATCHED)
                                                       |
                                      (Generates Pickup & Delivery OTPs)
                                      (Stores SHA-256 Hashes in DB)
                                                       |
                                           (Creates Shipment Record)
                                                       |
                                     (Creates Escrow Ledger Record: PENDING)
                                                       |
[Shipper] --(Deposits Funds via Telebirr)--> [POST /api/escrow/deposit]
                                                       |
                                         (Escrow Status = LOCKED)


Flow 4: Shipment Execution, Tracking & OTP Handover
----------------------------------------------------------------------------------------------------
[Driver]  --(Arrives at Pickup Site)
[Shipper] --(Provides Pickup OTP to Driver)
[Driver]  --(Inputs Pickup OTP)-----------> [POST /api/shipments/:id/pickup-verify]
                                                       |
                                           (Hashes input with SHA-256)
                                           (Verifies match with pickup_otp_hash)
                                                       |
                                           (Shipment & Load status = IN_TRANSIT)
                                                       |
[Driver]  --(Drives Cargo & Transmits GPS)-> [POST /api/tracking/location]
                                                       |
                                           (Saves telemetry in location_breadcrumbs)
                                           (Updates driver live position)
                                                       |
[Driver]  --(Arrives at Destination)
[Receiver]--(Provides Delivery OTP to Driver)
[Driver]  --(Inputs Delivery OTP)---------> [POST /api/shipments/:id/delivery-verify]
                                                       |
                                           (Hashes input with SHA-256)
                                           (Verifies match with delivery_otp_hash)
                                                       |
                                           (Shipment & Load status = DELIVERED)
                                           (Escrow status = RELEASED)
                                           (Driver Payout Available)


Flow 5: Dispute Escalation & Admin Resolution
----------------------------------------------------------------------------------------------------
[Shipper/Driver] --(Opens Dispute)-------> [POST /api/disputes]
                                                       |
                                           (Dispute status = OPEN)
                                           (Shipment status = DISPUTED)
                                           (Escrow status = DISPUTED - Frozen)
                                                       |
[Admin] --(Reviews Evidence & Resolves)--> [POST /api/admin/disputes/:id/resolve]
                                                       |
                        +------------------------------+------------------------------+
                        |                                                             |
            [Action == REFUND_SHIPPER]                                    [Action == RELEASE_CARRIER]
                        |                                                             |
             (Escrow status = REFUNDED)                                    (Escrow status = RELEASED)
             (Shipper Balance Credited)                                    (Carrier Payout Released)

9. ADMIN OPERATIONS SUITE & AUDIT LOGGING SYSTEM
====================================================================================================
The backend features an administrative suite accessible exclusively to `ADMIN` authenticated users:

Admin API Surface (32 Verified Core Endpoints):
- Dashboard & Overview: GET /api/admin/dashboard, GET /api/admin/analytics, GET /api/admin/system-health
- Detailed Metrics: GET /api/admin/stats/* (overview, users, drivers, companies, vehicles, deliveries, disputes)
- User Management: GET /api/admin/users, GET /api/admin/users/:id, PATCH /api/admin/users/:id,
  POST /api/admin/users/:id/suspend, POST /api/admin/users/:id/activate, DELETE /api/admin/users/:id
- Identity Verification: GET /api/admin/kyc, POST /api/admin/kyc/:id/approve, POST /api/admin/kyc/:id/reject
- Vehicle Oversight: GET /api/admin/vehicles, POST /api/admin/vehicles/:id/verify, POST /api/admin/vehicles/:id/reject
- Load Oversight: GET /api/admin/loads, GET /api/admin/loads/:id, PATCH /api/admin/loads/:id
- Dispute Management: GET /api/admin/disputes, POST /api/admin/disputes/:id/resolve, POST /api/admin/disputes/:id/reject
- Security Audit Logs: GET /api/admin/audit-logs, GET /api/admin/audit-logs/export

Audit Logging Infrastructure:
Every administrative state change (user suspension, KYC approval, vehicle verification, dispute resolution, 
role update) invokes the `audit_logs` record writer. Audit log entries are immutable and retain user ID, 
action identifier, resource target, JSON payload delta, client IP address, and server timestamp.
